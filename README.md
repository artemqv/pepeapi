# PepeAPI / PepeChat

**PepeAPI** — учебный backend мессенджера на Go. **PepeChat** — его минимальная веб-страница для общения через WebSocket. Проект развивается поэтапно: от HTTP API и PostgreSQL к чату в реальном времени, а затем — к микросервисной архитектуре.

> **Статус на 29 октября 2026 года:** в ветке `dev` реализованы REST-маршруты, PostgreSQL, простой веб-интерфейс и WebSocket-рассылка. **WebSocket-сообщения сейчас получают все подключённые клиенты, независимо от указанного `chatID`; в PostgreSQL они не сохраняются.** Аутентификации и контроля доступа пока нет. Это учебный прототип, **не готовый к публикации в открытом интернете**.

## Что уже умеет приложение

### REST API

- Создавать пользователей с уникальными именами.
- Создавать пустые чаты.
- Добавлять участников в чат.
- Сохранять сообщения в PostgreSQL **через REST**.
- Возвращать историю сообщений конкретного чата.
- Возвращать список чатов пользователя.
- Передавать контекст запросов из HTTP-обработчиков в repository.

### WebSocket и интерфейс

- Отдавать веб-страницу по `GET /`.
- Устанавливать WebSocket-соединение через `GET /chats/{chatID}/ws`.
- Принимать текстовые сообщения от подключённых браузеров.
- Рассылать сообщение всем активным WebSocket-клиентам, включая отправителя.
- Управлять подключениями через `Hub`, каналы и goroutines.
- Открывать интерфейс с другого устройства, если оно может подключиться к серверу по сети.

### Пока не работает как полноценный мессенджер

- `chatID` в **WebSocket** пока не используется для фильтрации рассылки; название «чат 13» в интерфейсе **не гарантирует изоляцию комнаты**.
- WebSocket-сообщения не сохраняются в PostgreSQL и пропадают после перезапуска/отключения.
- Существующая REST-история и WebSocket-рассылка пока независимы.
- Введённое в браузере имя — только текстовая подпись, не подтверждённый пользователь.
- Нет логина, пароля, сессий, JWT и серверной проверки участия в чате.
- Нет автоматической синхронизации пропущенных WebSocket-сообщений после переподключения.

## Как устроена архитектура

### REST: запись и чтение из PostgreSQL

```text
Браузер / curl
      |
      | HTTP + JSON
      v
  http.ServeMux
      |
      v
  REST Handler
      |
      v
  Go interface
      |
      v
  database.Repository
      |
      v
     pgxpool
      |
      v
   PostgreSQL
```

HTTP-обработчики проверяют входные данные, вызывают методы repository и формируют HTTP-ответ. Repository выполняет SQL-запросы.

### WebSocket: обмен между браузерами

```text
Браузер A                  Браузер B
    |                          ^
    | WebSocket                | WebSocket
    v                          |
websocketHandler        websocketHandler
    |                          ^
    | hub.broadcast            | client.send
    v                          |
                  Hub.Run()
              (одна goroutine)
                    |
         рассылка всем клиентам
```

**На текущем этапе эти две схемы не соединены:** `hub.broadcast` не вызывает `CreateMessage`, а `POST /chats/{chatID}/messages` не публикует WebSocket-события.

### Почему используются каналы

`Hub.Run()` единолично изменяет `clients` и читает команды из каналов `register`, `unregister`, `broadcast`. Это позволяет не блокировать общую `map` мьютексом в текущем варианте.

У каждого `Client` есть буферизированный `send chan []byte`. Отдельная goroutine последовательно вызывает `conn.WriteMessage()` для этого клиента, чтобы не допустить одновременных записей в одно WebSocket-соединение.

## Запуск проекта локально

### Требования

- Linux, macOS или Windows с Go версии из `go.mod` (для проверки: `go version`).
- PostgreSQL, доступный на `localhost:5432`.
- Браузер (например, Firefox).
- По желанию — Docker для PostgreSQL.

### 1. Получить код

```bash
git clone https://github.com/artemqv/pepeapi.git
cd pepeapi
git switch dev
go mod download
```

Если проект уже скачан, достаточно перейти в его корень.

### 2. Поднять PostgreSQL

В коде `cmd/server/main.go` сейчас **жёстко указана** строка подключения:

```text
postgres://app:secret@localhost:5432/myapi?sslmode=disable
```

Для локальной разработки можно создать контейнер БД:

```bash
docker run -d \
  --name pepeapi-postgres \
  -e POSTGRES_USER=app \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=myapi \
  -p 127.0.0.1:5432:5432 \
  -v pepeapi-pgdata:/var/lib/postgresql/data \
  postgres:16
```

> Если база/контейнер уже существуют, не запускайте вторую копию на том же порту. `secret` — **учебный пароль**, не для публичного окружения. При первом запуске PostgreSQL требуется небольшое время на инициализацию.

Проверить:

```bash
docker ps
docker logs pepeapi-postgres
```

Если контейнер уже создан, но остановлен:

```bash
docker start pepeapi-postgres
```

### 3. Запустить сервер

Из корня:

```bash
go run ./cmd/server
```

Или из `cmd/server`:

```bash
go run .
```

**Не запускайте `go run main.go`** — такой запуск не включает соседние `hub.go`, `websocket.go` и `page.go` и приводит к ошибкам вида `undefined: websocketHandler`.

При запуске приложение:

1. Инициализирует OpenTelemetry.
2. Подключается к PostgreSQL.
3. Создаёт отсутствующие таблицы.
4. Запускает `Hub.Run()` в отдельной goroutine.
5. Регистрирует HTTP/WebSocket-маршруты.
6. Начинает слушать порт `8080` (`Addr: ":8080"`).

Открыть страницу:

```text
http://localhost:8080/
```

Если всё настроено, появится PepeChat с полями «Имя» и «Номер чата».

## REST API

Базовый адрес: `http://localhost:8080`. `chatID` и `userID` в путях — положительные целые числа.

| Метод | Маршрут | Назначение | Успех в текущем коде |
| --- | --- | --- | --- |
| `GET` | `/` | HTML-страница PepeChat | `200` |
| `POST` | `/users` | Создать пользователя | **`200`** (в handler нет `WriteHeader(201)`) |
| `POST` | `/chats` | Создать чат | `201` |
| `POST` | `/chats/{chatID}/members` | Добавить участника | `201`, без тела |
| `POST` | `/chats/{chatID}/messages` | Сохранить сообщение в БД | `201` |
| `GET` | `/chats/{chatID}/messages` | Получить историю чата | `200` |
| `GET` | `/users/{userID}/chats` | Получить чаты пользователя | `200` |
| `GET` | `/chats/{chatID}/ws` | WebSocket Upgrade | `101` при успешном handshake |
| `GET` | `/items/{id}` | Старый учебный маршрут | `200`, `404` и др. |

### POST /users

```bash
curl -i -X POST http://localhost:8080/users \
  -H 'Content-Type: application/json' \
  -d '{"username":"artem_demo"}'
```

Пример JSON-ответа (ID будет свой):

```json
{"id":1,"username":"artem_demo"}
```

`username` обязателен и уникален. Повторное имя вызовет ошибку ограничения PostgreSQL; текущий API ещё не переводит её в `409 Conflict`.

### POST /chats

```bash
curl -i -X POST http://localhost:8080/chats
```

Пример:

```json
{"id":13}
```

Новый чат пока пуст: участников надо добавить отдельно.

### POST /chats/{chatID}/members

```bash
curl -i -X POST http://localhost:8080/chats/13/members \
  -H 'Content-Type: application/json' \
  -d '{"user_id":1}'
```

Успех: `201 Created` без JSON-тела. Повторное добавление той же пары `(user_id, chat_id)` нарушает составной первичный ключ.

### POST /chats/{chatID}/messages

```bash
curl -i -X POST http://localhost:8080/chats/13/messages \
  -H 'Content-Type: application/json' \
  -d '{"user_id":1,"text":"Здарова, братан!"}'
```

Пример:

```json
{"id":2,"text":"Здарова, братан!","user_id":1,"chat_id":13}
```

**Это именно REST-операция с записью в PostgreSQL.** Текущая версия не рассылает созданное таким способом сообщение через WebSocket.

### GET /chats/{chatID}/messages

```bash
curl -i http://localhost:8080/chats/13/messages
```

Пример:

```json
[
  {"id":2,"text":"Здарова, братан!","user_id":1,"chat_id":13},
  {"id":3,"text":"Привет!","user_id":2,"chat_id":13}
]
```

Сообщения отсортированы по `id ASC`. **Если записей в данном чате нет, текущий код возвращает `null`**, потому что использует `var messages []Message` и не заполняет его. Это не ошибка подключения: позже заменим на `make([]Message, 0)`, чтобы получать `[]`.

### GET /users/{userID}/chats

```bash
curl -i http://localhost:8080/users/1/chats
```

Пример:

```json
[{"id":5},{"id":13}]
```

Для пользователя без чатов возвращается `[]`.

### Обработка ошибок

- Некорректные ID, пустые обязательные поля и невалидный JSON обычно дают `400 Bad Request`.
- Ошибки PostgreSQL сейчас нередко превращаются в `500 Internal Server Error`, в том числе ошибки уникальности и внешних ключей.
- Маршрут `/items/{id}` отдельно обрабатывает отсутствие записи как `404 Not Found`.
- Отсутствие аутентификации и контроля доступа — **неустранённая проблема безопасности**.

## Полный сценарий работы с REST

Выполнить команды в отдельном терминале при запущенном сервере:

```bash
# 1. Создаём двух пользователей (имена должны быть новыми)
curl -i -X POST http://localhost:8080/users \
  -H 'Content-Type: application/json' -d '{"username":"artem_demo"}'

curl -i -X POST http://localhost:8080/users \
  -H 'Content-Type: application/json' -d '{"username":"sergey_demo"}'

# 2. Создаём чат
curl -i -X POST http://localhost:8080/chats
```

Затем **подставьте реальные ID**, полученные из ответов, вместо условных `1`, `2`, `13`:

```bash
# 3. Добавляем участников
curl -i -X POST http://localhost:8080/chats/13/members \
  -H 'Content-Type: application/json' -d '{"user_id":1}'

curl -i -X POST http://localhost:8080/chats/13/members \
  -H 'Content-Type: application/json' -d '{"user_id":2}'

# 4. Отправляем сообщение через REST
curl -i -X POST http://localhost:8080/chats/13/messages \
  -H 'Content-Type: application/json' \
  -d '{"user_id":1,"text":"Привет из REST!"}'

# 5. Читаем историю и список чатов
curl -i http://localhost:8080/chats/13/messages
curl -i http://localhost:8080/users/1/chats
```

## WebSocket и Hub

### Как подключается браузер

HTTP-маршрут из `cmd/server/main.go`:

```go
mux.HandleFunc(
    "GET /chats/{chatID}/ws",
    websocketHandler(hub, logger),
)
```

Клиент отправляет HTTP-запрос с `Upgrade: websocket`, сервер при успехе отвечает `101 Switching Protocols`. После handshake данные передаются по одному длительно живущему WebSocket-соединению.

Адрес для локальной проверки:

```text
ws://localhost:8080/chats/13/ws
```

> **Внимание:** хотя путь содержит `13`, текущий `websocketHandler` **не читает `r.PathValue("chatID")`**, а `Hub` не группирует подключения по комнатам. Клиенты `/chats/13/ws` и `/chats/21/ws` сейчас получают одну и ту же рассылку.

### Что делает Hub

`cmd/server/hub.go` содержит:

```go
type Client struct {
    conn *websocket.Conn
    send chan []byte
}

type Hub struct {
    clients    map[*Client]struct{}
    register   chan *Client
    unregister chan *Client
    broadcast  chan []byte
}
```

- `register` добавляет активное соединение в `clients`.
- `broadcast` отправляет входящие байты в `send` каждого клиента.
- `unregister` удаляет клиента и закрывает его канал исходящих сообщений.
- Если буфер `send` заполнен, Hub исключает медленного клиента, чтобы тот не тормозил всех остальных.

`websocket.go` читает текстовые кадры через `ReadMessage()` и передаёт их в `hub.broadcast`. Отдельная goroutine пишет в WebSocket через `WriteMessage()`.

Сейчас это **текстовая рассылка**, без JSON-протокола сообщений и без базы данных. Установлен предел чтения `4096` байт на сообщение.

### Проверка из консоли Firefox

Открыть `http://localhost:8080/`, нажать `Ctrl+Shift+K` и выполнить:

```javascript
var ws = new WebSocket(`ws://${location.host}/chats/13/ws`);
ws.onopen = () => console.log('WebSocket connected');
ws.onmessage = event => console.log('Message:', event.data);
ws.onclose = event => console.log('Closed:', event.code);
```

Когда состояние `ws.readyState` стало `1` (`OPEN`):

```javascript
ws.send('Привет из Firefox!');
```

Во второй вкладке повторить подключение. Сообщение из первой вкладки должно отобразиться во второй и у самого отправителя.

Если открывали JSON-ответ через `/users/1/chats`, Firefox JSON Viewer может ограничивать WebSocket-подключение политикой CSP. Для консольных экспериментов используйте обычную HTML-страницу `/`.

## Веб-интерфейс PepeChat

Файл: `cmd/server/web/index.html`.

Возможности интерфейса:

- Поле «Имя».
- Поле с номером чата.
- Кнопка «Подключиться».
- Статус соединения и кнопка «Отправить».
- Вывод полученных сообщений в общий список.
- Адаптация под узкий экран телефона.

HTML загружается из скомпилированного Go-бинарника с помощью `//go:embed web/index.html` в `page.go`.

### Как работает кнопка «Подключиться»

JavaScript проверяет имя и номер чата, затем пытается открыть:

```text
/chats/<chatID>/ws
```

Если это не удаётся, страница пробует старый адрес `/ws`. **В актуальной ветке `dev` отдельный `/ws` не зарегистрирован** — этот fallback оставлен для совместимости со старым учебным примером.

При успешном подключении активируется кнопка отправки. Имя подставляется к тексту сообщения на стороне браузера:

```text
Артём: Привет!
```

Это **не авторизация**. Любой посетитель может указать любое имя.

Сейчас в HTML используется картинка с внешнего CDN для логотипа; при недоступности этого ресурса она может не загрузиться. Для независимого развёртывания стоит сохранить разрешённый к использованию файл в проекте и отдавать его локально.

### Отправка сообщений с интерфейса

1. Открыть `http://localhost:8080/`.
2. Вписать имя и произвольный положительный номер чата, например `13`.
3. Нажать «Подключиться».
4. Дождаться статуса подключения.
5. Вписать текст и нажать «Отправить».
6. Получить сообщение в этой и других подключённых вкладках.

**Это демонстрация real-time доставки, не сохранённый чат.** В REST-истории эти сообщения не появятся.

## Два устройства в одной сети

Для локального теста Go-сервер работает на компьютере с Linux. Оба устройства должны иметь сетевой доступ к нему.

1. Запустить `go run ./cmd/server`.
2. Узнать локальный IP компьютера:

   ```bash
   hostname -I
   ```

3. Если адрес, например, `192.168.1.105`, открыть на телефоне:

   ```text
   http://192.168.1.105:8080/
   ```

4. Открыть тот же интерфейс на ноутбуке.
5. Нажать «Подключиться» на обоих устройствах и отправить сообщения.

На телефоне **нельзя использовать `localhost:8080`** для доступа к серверу на ноутбуке: `localhost` телефона означает сам телефон.

При проблемах проверьте сетевую изоляцию Wi-Fi, порт `8080`, firewall и то, что Go-процесс слушает `:8080`.

> Номер чата в HTML пока не влияет на маршрутизацию WebSocket-сообщений; разные номера не изолируют пользователей.

## Удалённое подключение через интернет

Локальный адрес `192.168.x.x` обычно недоступен из чужой сети. Для удалённого подключения нужен публично доступный сервер, защищённый туннель или приватная VPN-сеть.

### Вариант A: приватная сеть (предпочтительно для тестирования)

[Tailscale](https://tailscale.com/docs/install/linux) даёт устройствам защищённый сетевой доступ, даже если они находятся в разных сетях. Участникам потребуется клиент и настройка доступа. Это предпочтительнее публичного туннеля для нашего пока незащищённого прототипа.

### Вариант B: Pinggy через SSH (без установки приложения у друга)

Pinggy может выдать временную публичную HTTPS-ссылку. Если SSH уже установлен на Linux, для создания туннеля дополнительный клиент может не понадобиться.

```bash
# Терминал 1: локальный сервер
go run ./cmd/server

# Терминал 2: HTTP/HTTPS-туннель
ssh -p 443 -R0:localhost:8080 free.pinggy.io
```

Сервис покажет ссылку формата:

```text
https://<выданный-поддомен>.a.pinggy.link
```

**Это пример формата — точное имя выдаётся при запуске.** Друг открывает HTTPS-адрес в обычном браузере. JS на странице сам выбирает `wss://` для HTTPS и `ws://` для HTTP.

Полезные ссылки: [документация HTTP-туннелей Pinggy](https://pinggy.io/docs/http_tunnels/), [примеры SSH-туннелей](https://pinggy.io/docs/guides/kubernetes/).

**КРИТИЧЕСКОЕ ПРЕДУПРЕЖДЕНИЕ:** публичный Pinggy URL открывает не только страницу, но и **все** HTTP-маршруты PepeAPI. В текущем коде нет авторизации, сервер доверяет подставленным ID и не проверяет участие в чатах. Любой посетитель, получивший доступ к ссылке, может обращаться к REST API, а также видеть WebSocket-рассылку. **Не подключайте публичный туннель к базе с настоящими данными и не используйте его для приватной переписки, пока не реализованы проверка доступа и аутентификация.** Для первого удалённого теста разумнее использовать приватную сеть либо ограниченный тестовый стенд с фиктивными данными и дополнительным доступом на уровне туннеля.

После эксперимента закрыть туннель клавишами `Ctrl+C` в его терминале. У бесплатных временных адресов URL может меняться при новом запуске.

### Вариант C: VPS

Для постоянного публичного использования понадобится размещение сервера, домен, HTTPS/WSS, конфигурация окружения, проверка пользователей и прав доступа. Сейчас этот вариант в проекте не реализован.

## PostgreSQL: таблицы и запросы

Таблицы создаются в `internal/database/postgres.go` функцией `CreateTables` с `CREATE TABLE IF NOT EXISTS`.

| Таблица | Назначение | Основные поля |
| --- | --- | --- |
| `users` | Пользователи | `id`, `username UNIQUE` |
| `chats` | Чаты | `id` |
| `chat_members` | Участники | `user_id`, `chat_id`, составной PK |
| `messages` | Сообщения REST | `id`, `text`, `user_id`, `chat_id` |
| `items` | Старый учебный API | `id`, `name`, `vremya` |

```text
users ----< chat_members >---- chats
  |                                |
  +-----------< messages >---------+
```

У `chat_members` внешние ключи с `ON DELETE CASCADE`. В `messages` есть внешние ключи на `users` и `chats`, но они **не заменяют** проверку участия автора в чате.

Если PostgreSQL работает в контейнере `pepeapi-postgres`:

```bash
docker exec -it pepeapi-postgres psql -U app -d myapi
```

Полезные SQL-запросы:

```sql
SELECT * FROM users ORDER BY id;
SELECT * FROM chats ORDER BY id;
SELECT * FROM chat_members ORDER BY chat_id, user_id;
SELECT id, text, user_id, chat_id FROM messages WHERE chat_id = 13 ORDER BY id;
SELECT chat_id FROM chat_members WHERE user_id = 1 ORDER BY chat_id;
```

Выйти из `psql`: `\q`.

## Логирование и трассировка

- JSON-логи `slog` отправляются в стандартный вывод.
- Middleware регистрирует метод, путь и длительность HTTP-запроса.
- `otelhttp` создаёт HTTP-трассировки.
- `internal/telemetry/telemetry.go` инициализирует OTLP HTTP-экспортёр и `TracerProvider` с `service.name=pepeapi`.
- В старом `GET /items/{id}` и `database.GetItem` дополнительно создаются пользовательские спаны.
- Реализована попытка graceful shutdown: до 10 секунд для HTTP и отдельный таймаут для OTel.

В репозитории **нет готового полного стека Jaeger/Grafana/Collector**. Если OTLP-приёмник не настроен, экспорт трассировок может выдавать ошибки. Наличие tracing ещё не означает готовый мониторинг или метрики.

## Тестирование

```bash
# Запуск существующих тестов
go test ./...

# Анализ типичных ошибок
go vet ./...
```

Тесты в репозитории пока сосредоточены на старом обработчике `GET /items/{id}` с `httptest` и GoMock. Автоматические тесты WebSocket Hub, клиентских соединений и REST-маршрутов мессенджера пока **не добавлены**.

Для проверки WebSocket полезно вручную открыть две вкладки или два устройства. Проверять следует отдельно:

- оба соединения установились;
- сообщение доставлено обоим клиентам;
- закрытие одного соединения не ломает другое;
- при перезапуске сервера браузер теряет текущую WebSocket-сессию;
- номера чатов **пока не изолируют** доставку (это ожидаемое ограничение текущего кода).

## Docker

В репозитории есть `Dockerfile` с multi-stage сборкой:

```bash
docker build -t pepeapi:dev .
```

Однако `cmd/server/main.go` использует DSN с `localhost:5432`. **Внутри Docker-контейнера `localhost` — это сам контейнер приложения**, а не контейнер базы или хост. Поэтому простого `docker run -p 8080:8080 pepeapi:dev` недостаточно для корректной работы с БД без дополнительных сетевых настроек.

Следующий инфраструктурный шаг — вынести DSN в переменные окружения и сделать Docker Compose.

## Известные ограничения и ошибки

| Симптом | Что проверить |
| --- | --- |
| `undefined: websocketHandler` | Запускать пакет `go run ./cmd/server` или `go run .`, а не только `main.go`. |
| Кнопка «Подключиться» не работает | Запущен ли сервер? Совпадает ли маршрут `/chats/{chatID}/ws`? Посмотреть Console / Network → WS в Firefox. |
| Firefox блокирует WebSocket через CSP | Не запускать код из JSON Viewer; открыть HTML-страницу `/`. |
| `ws is not defined` в консоли | Создать `var ws = new WebSocket(...)` в **текущей** вкладке. |
| `405 Method Not Allowed` на истории | Проверить регистрацию GET-маршрута и перезапуск сервера. |
| История сообщений возвращает `null` | В этом чате нет REST-сообщений; `nil`-срез кодируется в `null`. |
| WebSocket-сообщений нет в PostgreSQL | Это пока ожидаемое поведение: WebSocket и REST-история не связаны. |
| Клиенты с разными `chatID` видят сообщения друг друга | `hub.go` рассылает **всем**; фильтрации по комнатам пока нет. |
| Телефон не открывает `localhost:8080` | Использовать локальный IP Linux или адрес приватного/публичного туннеля. |
| `500` при создании пользователя/сообщения | Проверить PostgreSQL, существование ID, уникальность username и логи сервера. |
| Из Docker не видно PostgreSQL | DSN указывает на контейнерный `localhost`. |
| Не работает туннель | Проверить, работает ли `localhost:8080` на хосте и жив ли SSH-процесс. |

## План дальнейшей разработки

### Ближайшая цель: сохранённый чат между двумя устройствами

1. **Разделение WebSocket по чатам.** Добавить `chatID` в `Client`, передавать его с сообщением, рассылать только клиентам соответствующего чата.
2. **Подлинная идентификация.** Реализовать вход пользователя; не доверять имени и `user_id`, присланным браузером.
3. **Проверка доступа.** Перед WebSocket Upgrade проверять существование чата и то, что подключающийся пользователь состоит в нём. Аналогично защитить REST-запросы.
4. **Сохранение сообщений.** Сначала проверять данные и записывать сообщение через `CreateMessage` в PostgreSQL, потом рассылать событие WebSocket-клиентам.
5. **Синхронизация истории.** При открытии страницы получать историю через REST; после потери соединения загружать пропущенные сообщения.
6. **Надёжность.** Ping/Pong, таймауты, корректное отключение клиентов и Hub, контроль размеров сообщений, защита от переполнения очередей.
7. **Безопасный удалённый доступ.** HTTPS/WSS, проверка `Origin`, конфигурация и ограничение доступа.
8. **Тесты.** Проверки прав доступа, доставки, отключений, БД и веб-сценариев.

> Важно: сохранение в PostgreSQL **перед** WebSocket-рассылкой не даёт абсолютной гарантии доставки. Для более надёжной системы позже понадобятся подтверждения, идентификаторы событий, повторная загрузка истории и, возможно, outbox.

### Затем — микросервисная архитектура

После того как мессенджер заработает как одно приложение, можно выделять сервисы по реальным границам ответственности:

```text
                 Frontend
                    |
                 API Gateway
                    |
         +----------+----------+
         |          |          |
   User Service Chat Service Message Service
                               |
                       event/message bus
                               |
                        Realtime Service
                               |
                            WebSocket
```

Планируемая архитектура — **не текущее состояние репозитория**. Пока всё запускается как один Go-процесс и использует общую PostgreSQL-базу. Разделение на сервисы потребует межсервисного взаимодействия, отдельного владения данными, обработки сбоев и распределённой трассировки.
